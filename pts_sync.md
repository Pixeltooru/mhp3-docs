# G-PTS & C-PTS: Двухуровневая архитектура синхронизации

Система **G-PTS (Global Persistent Tracking Sequence)** и **C-PTS (Chat Persistent Tracking Sequence)** — это механизм, превращающий ненадежную сеть в строго упорядоченную систему событий с двухуровневой синхронизацией.

## 🎬 Концепция "Ленты и Проигрывателей"

Представь, что история событий пользователя — это кинопленка (Sequence). Каждый кадр на ней имеет номер: 1, 2, 3... (это и есть G-PTS).

### Основные компоненты:

- **Кинопленка (G-PTS)** — одна на пользователя. Она хранится на сервере в `updates_history`.
- **Проигрыватели (Устройства)** — их может быть много (Смартфон, ПК, Планшет).
- **Курсор (Playhead)** — у каждого проигрывателя есть свой курсор, число, на котором он сейчас остановился.

### Как это работает на практике:

1. **Сервер**: Генерирует событие №100 (G-PTS=100).
2. **Смартфон (онлайн)**: Получил событие №100, обновил свой локальный G-PTS до 100. Отправил ACK серверу: "Я, Смартфон, видел всё до 100".
3. **ПК (оффлайн)**: Его локальный G-PTS замер на 95.
4. **Когда ПК включится**: Он пришлет handshake(last_g_pts=95). Сервер посмотрит в "ленту" и отмотает события с 96 по 100 специально для ПК.

---

## 🏗️ Фундаментальные определения

Система базируется на двух независимых счетчиках:

### G-PTS (Global Persistent Tracking Sequence)
- **Принадлежность**: Индивидуально для каждого `user_id`.
- **Назначение**: Синхронизация "входящей корзины" обновлений. Любое событие (новое сообщение в любом чате, изменение профиля, блокировка, реакция) инкрементирует G-PTS пользователя.
- **Гарантия**: Если у пользователя на смартфоне G-PTS=100, а на сервере G-PTS=105, клиент точно знает, что он пропустил 5 любых событий в своей экосистеме.

### C-PTS (Chat Persistent Tracking Sequence)
- **Принадлежность**: Общий для всех участников конкретного `chat_id`.
- **Назначение**: Строгий порядок сообщений внутри переписки.
- **Гарантия**: Позволяет обнаруживать "дыры" в конкретном чате и запрашивать недостающие фрагменты истории.

## � Логика по типам сущностей

### 2.1. Личные чаты (1-on-1)
- **Счетчик**: У каждого чата свой C-PTS.
- **Событие**: Когда Пользователь А пишет Пользователю Б:
  1. Генерируется `message_id` (UUID v7).
  2. C-PTS чата инкрементируется (общий для обоих).
  3. У Пользователя А инкрементируется его личный G-PTS (событие: "я отправил").
  4. У Пользователя Б инкрементируется его личный G-PTS (событие: "мне пришло").
- **Зачем**: Это позволяет обоим устройствам синхронизировать статус сообщения (отправлено/доставлено/прочитано) через глобальную ленту обновлений.

### 2.2. Групповые чаты (Groups)
- **Счетчик**: Единый C-PTS на всю группу.
- **Событие**: Сообщение от участника увеличивает C-PTS группы.
- **Рассылка**: Сервер создает запись в `updates_history` для каждого участника группы с их личным инкрементом G-PTS.
- **Зачем**: Чтобы клиент не опрашивал 100 чатов при входе в сеть, а просто спросил: "Дай мне всё, что изменилось в моем G-PTS с номера 500 по 600".

## 🗄️ Схема данных (Database Blueprint)

Для реализации без пробелов сервер должен использовать три таблицы:

### user_states
Хранит текущий `last_g_pts` для каждого пользователя.
```sql
CREATE TABLE user_states (
    user_id UUID PRIMARY KEY,
    last_g_pts BIGINT NOT NULL DEFAULT 0,
    updated_at TIMESTAMP DEFAULT NOW()
);
```

### chat_states
Хранит текущий `last_c_pts` для каждого чата.
```sql
CREATE TABLE chat_states (
    chat_id UUID PRIMARY KEY,
    last_c_pts BIGINT NOT NULL DEFAULT 0,
    updated_at TIMESTAMP DEFAULT NOW()
);
```

### updates_history
```sql
CREATE TABLE updates_history (
    id BIGSERIAL PRIMARY KEY,
    user_id UUID NOT NULL,
    g_pts BIGINT NOT NULL,
    chat_id UUID,
    c_pts BIGINT,
    event_type VARCHAR(50) NOT NULL,
    event_data JSONB NOT NULL,
    created_at TIMESTAMP DEFAULT NOW(),
    INDEX idx_user_g_pts (user_id, g_pts),
    INDEX idx_chat_c_pts (chat_id, c_pts)
);
```

## 🔄 Алгоритм синхронизации (Step-by-Step)

### Шаг 1: Handshake (Рукопожатие)
Клиент при подключении шлет `SessionHandshake`:
```json
{
    "last_known_g_pts": 1050,
    "known_chats": {
        "chat_A": 40,
        "chat_B": 12
    }
}
```

### Шаг 2: Анализ разрыва (Gap Analysis)
Сервер смотрит:
- Актуальный G-PTS пользователя в базе — 1100.
- Разница (Gap) = 50 событий.
- Сервер не шлет "новые" сообщения. Он шлет `updates_diff(1051, 1100)`.

### Шаг 3: Обработка на клиенте
Клиент получает пачку событий. Для каждого события:
1. Записать сообщение в локальную БД чата.
2. Обновить локальный C-PTS чата.
3. Обновить локальный G-PTS.
4. Только после обработки всей пачки статус сессии переходит в `READY`.

---

## 🚨 Обработка конфликтов и "Дырок"

### Ситуация А: Пропуск G-PTS
Клиент получает живое сообщение через сокет с `g_pts=1105`, но его последний локальный — 1100.
- **Действие**: Клиент игнорирует (кладет в буфер) это сообщение и немедленно запрашивает `SyncDiff` для 1101-1104.
- **Почему**: Нельзя обрабатывать 1105, не зная, что было в 1101 (там могло быть удаление аккаунта или выход из группы).

### Ситуация Б: Пропуск C-PTS (внутри чата)
G-PTS идут по порядку, но в конкретном чате пришло сообщение с `c_pts=50`, а последнее было 45.
- **Действие**: Это сигнал о повреждении данных на сервере или глубокой очистке истории. Клиент должен пометить чат как "требующий полной перезагрузки" и очистить кеш этого чата.

---

## ✅ Протокол ACK (Подтверждение)

Чтобы сервер мог безопасно чистить `updates_history`, клиент должен подтверждать получение.

### Механизм подтверждения:
- Раз в 10-20 секунд или после получения пачки событий клиент шлет `AckBatch(g_pts=1100)`.
- Сервер помечает: "Все устройства пользователя X получили данные до 1100".

### Фоновая очистка (Cleanup Task)
Удаляет из `updates_history` записи, которые:
1. Старее `HISTORY_TTL` (20 дней).
2. И подтверждены всеми устройствами пользователя (или устройствами, заходившими в последние 30 дней).

# MHP3 Standard: Строгая спецификация синхронизации

## 1. Формальная модель состояний (State Machine)

Чтобы два клиента работали идентично, они должны следовать строгому конечному автомату.

### Состояния клиента:
1. **OFFLINE**: Соединение отсутствует.
2. **HANDSHAKING**: Соединение установлено, отправлен `SessionHandshake`, ожидание `SessionEstablished`.
3. **SYNCING**: Получен `SessionEstablished`, клиент получает поток `msg_delivery` для закрытия Gap. Все исходящие сообщения в этом состоянии ставятся в очередь (Buffer).
4. **READY**: Локальный G-PTS == Максимальный G-PTS сервера на момент Handshake. Разрешена отправка.

**Правило №1 (Strict Transition):** Переход в `READY` невозможен, пока в локальной БД есть "дыры" в G-PTS или C-PTS.

---

## 2. Алгоритм "Continuity Guard" (Защита от дыр)

Самая большая проблема — когда события приходят не по порядку или теряются.

### Инвариант G-PTS:
Для любого нового пакета $P$ с $G\_PTS_{new}$:
- Если $G\_PTS_{new} = G\_PTS_{local} + 1$: **Принять**, инкрементировать локальный счетчик.
- Если $G\_PTS_{new} \leq G\_PTS_{local}$: **Игнорировать** (дубликат).
- Если $G\_PTS_{new} > G\_PTS_{local} + 1$: **Заблокировать поток**, перейти в состояние `SYNCING`, инициировать `updates_get_diff(G_PTS_local + 1, G_PTS_new)`.

### Инвариант C-PTS:
C-PTS внутри чата должен быть непрерывным **в контексте глобальной ленты**. Если в `updates_history` для чата А пришло событие с $C\_PTS = 50$, а последнее было $45$, это означает, что сервер удалил часть истории чата (например, по требованию GDPR или очистки).
- **Действие**: Клиент обязан пометить локальный кеш чата как `INCONSISTENT` и перекачать последние 50 сообщений через Snapshot API.

---

## 3. Атомарность на сервере (Server-side Integrity)

Чтобы документация не позволяла реализовать сервер с ошибками гонки (Race Conditions):

**Правило №2 (Atomic Write):**
Любая операция изменения состояния (отправка сообщения, реакция) должна выполняться в одной транзакции БД/Redis:
1. `SELECT NEXTVAL(g_pts_sequence_for_user)` 
2. `SELECT NEXTVAL(c_pts_sequence_for_chat)` 
3. `INSERT INTO updates_history (...)` 
4. `INSERT INTO messages (...)` 
5. `COMMIT` 

*Если шаг 1-5 не атомарны, клиент получит G-PTS=100, но не найдет записи в истории при синхронизации другого устройства.*

---

## 4. Спецификация Handshake (Zero-Ambiguity)

При `SessionHandshake` клиент передает не просто "что знает", а **границы своих знаний**.

```protobuf
message SessionHandshake {
    uint64 last_g_pts = 1;         // Последний G-PTS, который клиент записал в БД
    map<string, uint64> c_pts_map = 2; // Карта {chat_id: last_c_pts}
}
```

### Алгоритм ответа сервера:
1. Найти `max_server_g_pts` для пользователя.
2. Если `max_server_g_pts - last_g_pts > HARD_HISTORY_LIMIT` (8 месяцев):
   - Вернуть `ERROR_PTS_TOO_OLD`.
   - Клиент обязан стереть локальную БД и начать `Cold Start`.
3. Иначе:
   - Отправить `SessionEstablished(current_max_g_pts)`.
   - Начать последовательную трансляцию всех `updates_history` от `last_g_pts + 1` до `current_max_g_pts`.

---

## 5. Дедупликация и 0-RTT (Idempotency Key)

Чтобы клиент мог слать сообщения мгновенно, не дожидаясь ACK, и не плодить дубли:

1. **Client-side**: Каждое сообщение генерирует `client_message_id` (UUID v7).
2. **Server-side**: 
   - Сервер проверяет в Redis: `EXISTS msg_id:{client_message_id}`.
   - Если существует: Сервер не создает новую запись, а возвращает **существующий** G-PTS и C-PTS для этого сообщения.
   - Это гарантирует, что при плохом интернете (Retry) в ленте событий не будет двух одинаковых сообщений с разными PTS.

---

## 6. Механизм "Якорения" (Anchoring) при Cold Start

Если клиент новый (G-PTS = 0):
1. Клиент делает `GET /api/v1/sync/snapshot`.
2. Сервер возвращает:
   - Текущий `anchor_g_pts` (например, 1,000,000).
   - Список последних 20 чатов и 20 сообщений в каждом.
3. Клиент записывает это в базу.
4. **Важно**: С этого момента клиент считает свой `last_g_pts = 1,000,000`. Все события > 1,000,000 он принимает через сокет, всё что < — игнорирует как старое.

---

## 7. Термины для документации


- **Gap (Разрыв)**: Ситуация, когда $PTS_{received} \neq PTS_{local} + 1$.
- **Snapshot (Снимок)**: Текущее состояние системы без истории, используемое для инициализации.
- **Reconciliation (Сверка)**: Процесс исправления расхождений между Redis и PostgreSQL.
- **Head of Log**: Текущий максимальный PTS в системе.
- **Tail of Log**: Самый старый PTS, доступный в `updates_history` (ограничен TTL).

## �� Алгоритм "Холодного старта" (Cold Start)

Это самый тонкий момент. Когда ты залогинился на абсолютно новом устройстве, у него `last_g_pts = 0`.

### Процесс Cold Start:

1. **Новое устройство**: Шлет handshake(last_g_pts=0).
2. **Сервер**: Смотрит в свою таблицу `updates_history`. Там лежат события, например, от G-PTS 500 до 1100 (все, что накопилось за время TTL — 20 дней).

#### Ситуация А (Данные есть в ленте):
Сервер начинает выстреливать в новое устройство все 600 событий (с 500 по 1100). Устройство их записывает и в конце говорит: "Теперь мой G-PTS = 1100".

#### Ситуация Б (Gap слишком большой):
Если самое старое событие в базе имеет G-PTS 500, а клиенту нужно от 0, сервер отвечает: `ERROR_PTS_TOO_OLD`.

**Действие клиента**: Клиент делает Snapshot Sync (запрашивает текущий список чатов и последние 20 сообщений через обычный API).

**Якорение (Anchoring)**: Вместе с ответом API сервер присылает текущий G-PTS=1100. Клиент записывает это число как свою стартовую точку. Всё, теперь он "в строю" и готов получать обновления 1101, 1102...

---

## 🔄 Почему PTS не должны быть разными для разных устройств?

Если бы мы делали разные PTS для Смартфона и ПК (например, у Смартфона свой счетчик, у ПК свой), мы бы получили ад:

1. **Серверу пришлось бы хранить дубликаты** всех событий для каждого устройства отдельно.
2. **Потеря синхронизации**: Если ты удалишь сообщение на Смартфоне, ПК об этом никогда не узнает, потому что у него "своя история".
3. **Сложность консистентности**: Поддержание согласованности между разными историями потребовало бы сложных алгоритмов разрешения конфликтов.

**Единый G-PTS гарантирует**, что все устройства видят одну и ту же вселенную событий в одном и том же порядке.

## 📊 Итоговая логика "Стандарта" (Multi-device Sync)

### На стороне Сервера (Таблица сессий):

Сервер должен знать, на каком этапе находится каждое устройство (для оптимизации чистки логов):

| User_ID | Device_ID | Last_Synced_G_PTS |
| :--- | :--- | :--- |
| user_1 | iphone_15 | 1100 |
| user_1 | macbook_pro | 1050 |

### На стороне Клиента (Локальная база):

Клиент хранит ровно одно число — `last_g_pts`.

### Логика "Прочтения" (Read Receipts):

Это событие тоже летит через PTS.
Если ты прочитал чат на iPhone, сервер генерирует событие `READ_CHAT` (chat_id: A, up_to_pts: 50) и присваивает ему G-PTS=1101.
Это событие прилетает на MacBook (у которого G-PTS был 1100).
MacBook видит G-PTS 1101, читает payload и понимает: "Ага, хозяин прочитал чат А на другом устройстве, убираю уведомление".

## 🎯 Резюме для документации

Чтобы не было "двух разных протоколов", стандарт гласит:

1. **G-PTS Identity**: G-PTS — это неизменяемый индекс в персональном логе обновлений пользователя. Он инвариантен для всех устройств пользователя.
2. **New Device Anchoring**: Новое устройство либо "проигрывает" лог обновлений из `updates_history`, либо выполняет "якорение" к текущему максимальному G-PTS сервера через Snapshot (если лог слишком старый).
3. **State Recovery**: Любой Gap (пропуск) в G-PTS на любом устройстве — это триггер для немедленного запроса `updates_get_diff` от последней известной точки этого устройства.

## Приоритет протокола (Primary Protocol)

**MHP3 (Modern Message Handshake Protocol v3.0)** является **основным и единственным приоритетным** протоколом передачи данных в системе. Все новые функции (сообщения, реакции, редактирование, статусы) реализуются исключительно через бинарный канал MHP3.

- **Legacy Support (MHP2/Socket.IO Events)**: Обычные события Socket.IO (`message_send`, `message_delivery`, `message_status_update`) оставлены исключительно для обратной совместимости в переходный период.
- **Обязательная миграция**: Все клиентские реализации должны использовать `mhp3_data` бинарный поток. Если данные (например, большие файлы или специфические метаданные) не могут быть переданы в одном пакете Protobuf, они должны быть разделены на управляющий пакет MHP3 и вспомогательный HTTP-запрос.

## Основные правила (Invariants)

1. **Монотонность G-PTS**: G-PTS для пользователя всегда растет. Не может быть ситуации, когда после G-PTS=10 пришел G-PTS=9.
2. **Монотонность C-PTS**: C-PTS для чата всегда растет. Порядок сообщений в чате строгий.
3. **Непрерывность**: Клиент должен получать события последовательно. Любой "пропуск" в номерах G-PTS — это сигнал о потере данных.
4. **Атомарность**: Инкремент G-PTS/C-PTS и запись в историю событий (`updates_history`) происходят в одной транзакции БД.
5. **Глобальная идентичность**: G-PTS инвариантен для всех устройств пользователя. Все устройства работают с одной и той же "лентой".
6. **Статус Доставлено (Delivered)**: Подтверждение доставки сообщения устройством (`DELIVERED`) является **G-PTS-событием**. Это гарантирует, что если у пользователя несколько устройств, все они узнают о том, что сообщение было доставлено на одно из них, и смогут синхронизировать состояние "галочек".

## Как реализовать на коленке

### Для Клиента:
- **Локальное хранилище**: Храни `last_g_pts` (последний глобальный PTS) + карту `{chat_id: last_c_pts}` для каждого чата.
- **Детекция Gap**: Если пришло событие с `g_pts=N`, а у тебя было `last_g_pts=N-2`, значит `N-1` потеряно. **Решение**: Немедленно делай `session_handshake` для докачки.
- **Оптимистичный ID**: Генерируй UUID v7 для `msg_send`. Если сервер ответит ошибкой, ты сможешь переотправить его с тем же ID, и сервер поймет, что это дубль.

### Для Сервера:
- **Fast Path (Redis)**: Используй `INCR mhp3:g_pts:{user}` и `INCR mhp3:c_pts:{chat}` для мгновенного получения номеров.
- **Slow Path (DB)**: Раз в 5 минут (или при простое) сливай значения из Redis в PostgreSQL через `GREATEST(current_pts, new_pts)`.
- **История**: Сохраняй `event_data` в JSONB. Это позволит тебе докачивать историю любой сложности (сообщения, реакции, удаления).
- **Сессии**: Храни таблицу активных устройств для оптимизации очистки старых событий.

## Алгоритм слияния (Merge/Reconciliation)

Для исключения дубликатов и обеспечения целостности при сбоях:

1. **Очередь Fallback**: Если БД лежит, пиши события в Redis List `g_pts:fallback_queue`.
2. **Безопасный UPSERT для G-PTS**:
   ```sql
   INSERT INTO user_states (user_id, last_g_pts)
   VALUES (:uid, :g_pts)
   ON CONFLICT (user_id)
   DO UPDATE SET last_g_pts = GREATEST(user_states.last_g_pts, EXCLUDED.last_g_pts);
   ```
3. **Безопасный UPSERT для C-PTS**:
   ```sql
   INSERT INTO chat_states (chat_id, last_c_pts)
   VALUES (:cid, :c_pts)
   ON CONFLICT (chat_id)
   DO UPDATE SET last_c_pts = GREATEST(chat_states.last_c_pts, EXCLUDED.last_c_pts);
   ```
4. **Результат**: Даже если задача синхронизации упадет на середине и перезапустится, данные не пострадают.

---

## Жизненный цикл события (G-PTS + C-PTS)

### Сценарий: Пользователь А пишет сообщение Пользователю Б в личный чат

1. **Событие**: Пользователь А шлет сообщение в чат Х.
2. **Инкремент C-PTS**: Сервер делает `C-PTS++` для чата Х (общий для обоих).
3. **Инкремент G-PTS**: 
   - Сервер делает `G-PTS++` для пользователя А (событие: "отправил").
   - Сервер делает `G-PTS++` для пользователя Б (событие: "получил").
4. **Запись**: Два события летят в `updates_history` (по одному для каждого пользователя).
5. **Доставка**:
   - Если Б онлайн: сервер шлет бинарный пакет `msg_delivery` через Socket.IO.
   - Если Б оффлайн: сервер шлет Push (FCM). Когда Б подключится, он получит это событие через `session_handshake`.
6. **Синхронизация устройств**: Все устройства пользователя А и Б получат свои события и обновят свои `last_g_pts`.

## Long-term Cold Sync (Холодная синхронизация)

Поскольку история событий в `updates_history` имеет плавающее окно (от **20 дней** до **8 месяцев**), возможна ситуация, когда клиент возвращается в сеть спустя очень долгий срок.

### 1. Плавающий TTL (Floating TTL/TTS)
В MHP3 реализована гибридная политика хранения истории:
- **Active User (20 дней)**: Если пользователь регулярно заходит в онлайн, сервер хранит только последние 20 дней истории событий. Этого достаточно для синхронизации при кратковременных обрывах связи.
- **Offline User (до 8 месяцев)**: Если пользователь ушел в оффлайн, окно хранения начинает "растягиваться" до 8 месяцев. Это позволяет получить все пропущенные события даже спустя полгода отсутствия.
- **Hard Delete (8 месяцев)**: Если пользователь не заходил в сеть более 8 месяцев, его история удаляется безусловно.

### 2. Детекция устаревания
Если `last_known_g_pts` клиента меньше, чем самый старый G-PTS, доступный в истории сервера (после применения плавающего окна):
- Сервер пришлет пакеты `msg_delivery`, но первый же пакет будет иметь `g_pts > last_known_g_pts + 1`.
- **Действие клиента**: При обнаружении такого разрыва (Gap) в самом начале потока синхронизации, клиент должен остановить обработку и инициировать **Cold Sync**.

### 3. Процесс Cold Sync
Холодная синхронизация подразумевает полную перезагрузку состояния вместо "проигрывания" истории:
1. **Сброс локального кеша**: Клиент помечает локальные события как "архивные" или очищает кеш (в зависимости от бизнес-логики).
2. **Запрос актуального состояния**: Клиент использует стандартные REST API эндпоинты (`/api/chats`, `/api/messages/last`) для получения текущего списка чатов и последних 20-50 сообщений.
3. **Якорение (Anchoring)**: После загрузки актуального состояния, клиент берет `current_g_pts` из ответа сервера и сохраняет его как свою новую точку отсчета.

### 4. Рекомендации по настройке
- **HISTORY_TTL_DAYS**: Рекомендуется держать историю не менее 14-28 дней. Увеличение срока повышает нагрузку на PostgreSQL, но снижает частоту "холодных" перезагрузок у редких пользователей.
- **Background Sync**: На мобильных устройствах рекомендуется использовать фоновые Push-уведомления (Silent Push) для обновления G-PTS в фоне, чтобы минимизировать вероятность Cold Sync.

---

## Secure Link (Доверенное звено)

Если клиент был оффлайн более **20 дней** или история на сервере была очищена, MHP3 предлагает механизм **Secure Link** для восстановления событий через другое устройство пользователя.

> [!TIP]
> **Рекомендация для клиента**: Если последнее успешное рукопожатие было более 20 дней назад, клиенту рекомендуется превентивно запросить список своих активных устройств для возможного восстановления истории, даже если сервер еще не удалил данные из горячего хранилища.

### 1. Сценарий использования
- У пользователя два устройства: Смартфон (Устройство А) и Планшет (Устройство Б).
- Смартфон был выключен 30 дней. Планшет регулярно синхронизировался.
- При включении Смартфон обнаруживает Gap в G-PTS, который сервер не может закрыть (история удалена).

### 2. Алгоритм восстановления (D2D Relay)
1. **Запрос**: Смартфон шлет `HistoryRecoveryRequest` с флагом `request_from_trusted_device = true`.
2. **Поиск**: Сервер проверяет, есть ли другие активные сессии (`sid`) у этого `user_id`.
3. **Уведомление**: Если Планшет онлайн, сервер ретранслирует ему запрос на восстановление.
4. **Передача**: Планшет выгружает локальную историю событий, шифрует её специально для Смартфона (используя эфемерный ключ из Noise Handshake) и отправляет серверу пакет `DeviceRelayRequest`.
5. **Реле**: Сервер, не имея доступа к содержимому, пересылает бандл Смартфону через `DeviceRelayResponse`.

### 3. Преимущества
- **Zero-Knowledge**: Сервер не хранит историю вечно, но пользователь не теряет данные.
- **End-to-End Security**: Передача данных между устройствами зашифрована ключами, которые знает только пользователь.
- **Автоматизация**: Процесс происходит незаметно для пользователя в фоне.

---

## Background Sync (Фоновая синхронизация)

Для мобильных клиентов, находящихся в фоновом режиме, поддержка постоянного Socket.IO соединения может быть затруднительна. MHP3 предоставляет облегченный механизм синхронизации через стандартный HTTP POST запрос.

### Алгоритм фоновой синхронизации:
1. **Trigger**: Клиент получает Silent Push (FCM) или срабатывает фоновый таймер ОС.
2. **Request**: Клиент отправляет бинарный `MHP3Envelope` (content: `updates_get_diff`) на эндпоинт `POST /api/mhp/updates/diff`.
3. **Auth**: Запрос должен содержать заголовок `Authorization: Bearer <JWT>`.
4. **Response**: Сервер возвращает бинарный `MHP3Envelope` (content: `updates_diff`) со всеми пропущенными событиями.
5. **Processing**: Клиент обрабатывает события локально и обновляет свой `last_g_pts`, не открывая сокет.

*Примечание*: Этот метод рекомендуется для экономии заряда батареи и быстрой подкачки событий при получении уведомлений.

# MHP3 Standard: Спецификация для Клиентов (Flutter & Forks)

## 1. Требования к Локальному Хранилищу (Local Persistence)

Любой клиент обязан поддерживать ACID-совместимое локальное хранилище (SQLite, Isar, Hive с транзакциями).

**Обязательные поля в локальной БД:**
1. **Global Metadata**: `last_g_pts` (int64).
2. **Chat Metadata**: Таблица или Map `chat_id -> last_c_pts`.
3. **Message Status**: Поле `sync_status` (ENUM: `SENDING`, `SENT`, `DELIVERED`, `READ`, `FAILED`).
4. **Idempotency Log**: Таблица `processed_uuids` (хранить последние 1000 UUID v7 для исключения дублей при переповторах от сервера).

---

## 2. Жизненный цикл сообщения: Алгоритм 0-RTT

Для обеспечения "Optimistic UI" и гарантии доставки, клиент обязан следовать этому циклу:

1. **UI Trigger**: Пользователь нажал "Отправить".
2. **Local Commit**: 
   - Генерируется `UUID v7`.
   - Сообщение записывается в локальную БД со статусом `SENDING` и временным `local_id`.
   - UI обновляется мгновенно.
3. **Transport**: Сообщение упаковывается в `MHP3Envelope(msg_send)` и улетает в сокет.
4. **Pending Queue**: Сообщение попадает в оперативную очередь `unacknowledged_messages`.
5. **Server ACK**:
   - Приходит `MHP3Envelope(msg_delivery)` с тем же `UUID`.
   - **Клиент обязан**: Обновить статус в БД на `SENT`, записать полученные `g_pts` и `c_pts`.
   - Удалить из `unacknowledged_messages`.

---

## 3. Алгоритм Обработки Входящего Потока (The Stream Processor)

Это сердце клиента. Он должен работать как **последовательный конвейер**.

```dart
// Псевдокод стандартного процессора MHP3 для Flutter
void onMessageReceived(MHP3Envelope envelope) {
  final int incomingGPts = envelope.pts;  
  if (incomingGPts == localStore.lastGPts + 1) {
    // 1. Идеальный случай: следующее событие
    applyEventToDatabase(envelope);
    localStore.lastGPts = incomingGPts;
  } 
  else if (incomingGPts > localStore.lastGPts + 1) {
    // 2. GAP DETECTED: пропуск данных
    pauseStreamProcessing();
    initiateSyncDiff(localStore.lastGPts + 1, incomingGPts);
  } 
  else {
    // 3. OLD EVENT: дубликат или запоздалый пакет
    ignoreEvent(); 
  }
}
```

**Правило №3 (No Partial Updates):** Клиент **запрещено** обновлять UI или базу данных сообщением, если его G-PTS создал "дыру". Сначала нужно закрыть Gap через `sync_diff`.

---

## 4. Правила для Форков (Fork Compliance)

Чтобы форк считался "MHP3-совместимым", он должен проходить следующие тесты:

1. **Strict Handshake**: Форк не имеет права запрашивать данные через REST API, минуя `session_handshake` в бинарном канале.
2. **Order Consistency**: Если форк отображает сообщения в порядке, отличном от возрастания C-PTS, он считается дефектным.
3. **Multi-device Friendly**: Если на другом устройстве (например, официальном) пришло событие `msg_delete` с G-PTS=500, форк **обязан** удалить это сообщение локально, даже если оно уже было прочитано.

---

## 5. Обработка фонового режима (Background/Push)

Для Flutter-клиентов стандарт определяет поведение при получении Push-уведомления:

1. Push (FCM/APNS) содержит только `g_pts` и краткий тизер.
2. **Запрещено** считать Push полноценным событием и обновлять `last_g_pts` только на его основе.
3. **Действие**: При открытии приложения клиент обязан выполнить `session_handshake(last_g_pts)`, чтобы получить реальное бинарное событие из `updates_history`. Push — это лишь сигнал "проснись и синхронизируйся".

---

## 6. Безопасность: Требование Noise Handshake

Клиент (Flutter) должен реализовывать `X25519` для обмена ключами.

1. При каждом холодном старте генерировать новую эфемерную пару.
2. Публичный ключ передается в `SessionHandshake`.
3. Все последующие `mhp3_data` пакеты (payload внутри Envelope) расшифровываются ключом, выведенным через HKDF из Shared Secret.
4. **Fork Rule**: Использование MHP3 без Noise-шифрования допускается только в `DEBUG` режиме. В `PRODUCTION` сервер обязан обрывать соединение.

---

## 7. Контроль целостности C-PTS (Per-Chat Check)

Даже если G-PTS идет по порядку, клиент должен проверять целостность внутри чата:

- Если в чате последнее сообщение имело `C-PTS = 10`, а новое пришло с `C-PTS = 15` (при этом G-PTS последовательен).
- **Причина**: Кто-то очистил историю на сервере или произошел программный сбой.
- **Реакция клиента**: Показывать системное сообщение: *"Часть истории этого чата была удалена"* и сбросить локальный счетчик C-PTS для этого чата на 15.

---

### Итог разработки стандарта:

Теперь документация закрывает все щели:
1. **Сервер** гарантирует атомарность и хранение истории.
2. **Транспорт** (Protobuf/Noise) гарантирует компактность и защиту.
3. **Клиент (Flutter/Fork)** гарантирует строгий порядок обработки и дедупликацию.

# MHP3 Protocol Standard: Advanced Synchronization Mechanisms

Данный документ определяет набор механизмов, обязательных для реализации сервером и клиентом MHP3. 
## 1. Версионирование протокола (Protocol Layers)

**Проблема:** Обновление протокола (добавление новых полей в Protobuf) не должно "ломать" старые клиенты и форки.

### Спецификация:

1. **`SessionHandshake`** должен содержать поле `layer`:
   ```protobuf
   message SessionHandshake {
       // ... (last_g_pts, c_pts_map, etc.)
       int32 layer = 10; // Обязательное поле. Клиент указывает версию протокола, которую он поддерживает.
   }
   ```
2. **Сервер обязан** знать текущую последнюю версию слоя (например, `LATEST_LAYER = 15`).
3. **Логика сервера:**
   - Если `client.layer == LATEST_LAYER`, сервер работает в штатном режиме.
   - Если `client.layer < LATEST_LAYER`, сервер **обязан** включить режим совместимости:
     - Не отправлять типы событий, появившиеся в слоях > `client.layer`.
     - При отправке существующих событий, не заполнять поля, добавленные в новых слоях.
4. **Логика клиента:** Клиент (Flutter/Fork) должен жестко зафиксировать номер слоя, который он реализует. При обновлении клиента номер слоя инкрементируется.

**Пример:** В слое 16 добавили `MessageReaction`. Сервер, видя, что клиент прислал `layer = 15`, просто не будет отправлять ему события типа `UpdateReaction`.

## 2. Контейнеры синхронизации состояния (State Containers)

**Проблема:** Отправка сотен событий по одному (`msg_delivery`) неэффективна, расходует батарею и создает излишнюю нагрузку на рендеринг UI в клиенте.

### Спецификация:

1. **Вводится новый `oneof` контейнер `Update`** вместо прямого `msg_delivery` в `MHP3Envelope`.

   ```protobuf
   // Основной конверт
   message MHP3Envelope {
       bytes id = 1;     // UUID v7
       // ...
       oneof content {
           // ... (SessionHandshake, MessageSend, etc.)
           Updates updates = 43;         // Пакет обновлений
           UpdateShort update_short = 44;  // Одиночное быстрое обновление
       }
   }

   // Пакет обновлений для закрытия "дыры"
   message Updates {
       repeated Update event = 1;      // Массив событий
       uint64 from_g_pts = 2;          // Начальный G-PTS в этом пакете
       uint64 to_g_pts = 3;            // Конечный G-PTS
       int32 count = 4;                // Общее количество событий
   }

   // Обертка для любого события
   message Update {
       uint64 g_pts = 1;
       uint64 c_pts = 2;               // Если применимо
       string chat_id = 3;             // Если применимо
       
       oneof event_data {
           MessageDelivery message = 10;
           MessageStatusUpdate status_update = 11;
           // ... другие типы событий
       }
   }
   ```

2. **Логика сервера:**
   - При `session_handshake` для закрытия Gap, сервер **обязан** группировать все пропущенные события в один или несколько пакетов `Updates`.
   - Для событий в реальном времени (например, статус "печатает") используется легковесный `UpdateShort`.
3. **Логика клиента (Flutter):**
   - При получении пакета `Updates` клиент **обязан** обрабатывать весь массив `event` внутри **одной транзакции** локальной базы данных (SQLite/Isar).
   - Только после успешного завершения транзакции клиент обновляет свой `last_g_pts` до `to_g_pts` из пакета.
   - UI обновляется один раз после завершения транзакции, а не на каждое сообщение.

## 3. Целостность сессии и состояния (Session Salt)

**Проблема:** Если сервер аварийно перезагружается и теряет состояние в Redis (например, счетчик PTS откатился), клиент об этом не узнает и окажется в состоянии десинхронизации.

### Спецификация:

1. **`SessionEstablished`** должен содержать `server_salt`:
   ```protobuf
   message SessionEstablished {
       // ... (user_id, pts_map, etc.)
       uint64 server_salt = 10; // Случайное число, генерируемое при старте сервера.
   }
   ```
2. **`SessionHandshake`** должен отправлять последнюю известную соль:
   ```protobuf
   message SessionHandshake {
       // ...
       int32 layer = 10;
       uint64 known_server_salt = 11; // Соль, полученная в прошлом `SessionEstablished`. 0 для новой сессии.
   }
   ```
3. **Логика сервера:**
   - При старте генерируется и хранится глобальный `server_salt`.
   - При получении `SessionHandshake`: если `known_server_salt != 0` и `known_server_salt != current_server_salt`, сервер понимает, что клиент имеет устаревшее состояние.
   - В этом случае сервер может принудительно разорвать сессию и вернуть ошибку `ERROR_STATE_RESET`, требуя от клиента полной повторной синхронизации.
4. **Логика клиента (Flutter):**
   - Клиент **обязан** сохранять `server_salt` в локальном хранилище.
   - При получении `SessionEstablished`, если `new_salt != stored_salt`, это сигнал о возможном сбросе состояния на сервере.
   - **Действие клиента:** Считать локальный кеш потенциально невалидным, очистить таблицы сообщений и медиа, инициировать `Cold Start` (Snapshot Sync). Это единственный способ гарантировать 100% консистентность.

## 4. Идемпотентность и подтверждение (Client Request ID)

**Проблема:** При нестабильной сети клиент может отправить `MessageSend` дважды. Сервер должен распознать дубликат.

### Спецификация:

1. **`MessageSend`** должен содержать `client_req_id`:
   ```protobuf
   message MessageSend {
       bytes client_req_id = 1; // UUID v7 или 16 случайных байт, сгенерированных клиентом.
       // ... (chat_id, payload, etc.)
   }
   ```
2. **Серверный ACK (подтверждение)** в виде `MessageDelivery` или специального `Ack` пакета должен возвращать этот `client_req_id`:
   ```protobuf
   message MessageDelivery {
       bytes client_req_id = 1; // Эхо `client_req_id` из `MessageSend` 
       bytes message_id = 2;    // Постоянный ID сообщения от сервера (UUID v7)
       // ...
   }
   ```
3. **Логика сервера:**
   - Сервер хранит хэш `client_req_id` в Redis с TTL (например, 5 минут).
   - Если приходит `MessageSend` с уже известным `client_req_id`, сервер не создает новое сообщение, а возвращает существующий `MessageDelivery` для этого запроса.
4. **Логика клиента (Flutter):**
   - При отправке сообщения клиент сохраняет `client_req_id` в Map `unacknowledged_messages`.
   - Получив `MessageDelivery`, клиент находит исходящее сообщение по `client_req_id` и обновляет его статус с `SENDING` на `SENT`, а также заменяет временный ID на постоянный `message_id`.
